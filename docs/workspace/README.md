# W3–6 主数据与门户验收

真实工作台沿用已确认的前端风格，使用 Snowy 内部/门户登录、MySQL 持久化及私有 MinIO 附件。离线 Demo 仍独立保留。

## 启动与账号

在仓库目录分别执行 `./scripts/start-backend.sh` 和 `./scripts/start-workspace.sh`。端口后端8080、工作台5175，均为开发服务。原 Snowy 工程通过 `./scripts/start-frontend.sh` 启动，原生菜单内有同一工作台。

首次本地开发执行 `node scripts/prepare-workspace-access.mjs`。登录信息只写入 Git 忽略、权限600的 `.runtime/workspace-access.md`；不会重置已有账号。正式人员通过原生账号管理分配组织、SUP-ADMIN/CAT-MGR/SQE角色、API权限与数据范围。门户账号在联系人详情绑定；保留原有验证码策略。

## 人工验收

1. 新建供应商：编码留空自动生成，或填写全局唯一自定义编码；合法信用代码可保存，当前组织重复代码被拒绝，初始状态潜在。刷新后数据仍在。
2. 搜索、组织/品类/状态/等级筛选与排序，导出匹配筛选的脱敏 Excel。
3. 编辑档案；过期版本返回冲突，不覆盖他人修改。
4. 上传PDF/PNG/JPEG资质并续期，保留旧版，按品类计算缺失资质。附件可授权预览与下载，不能匿名下载或被另一组织复用。
5. 建立管理员与其他联系人，分配多个角色并绑定独立门户账号。最后有效管理员不能停用；停用账号踢出会话且不能再登录。
6. 切换另一个组织、SELF范围、只读用户、其他供应商门户，验证列表/详情/修改/附件/导出均不扩展授权。
7. 查看资质预警及签名业务记录；重复扫描不重复提醒，提醒遵循数据范围。

## 范围与限制

当前交付主数据、资质、联系人及门户基础；真实准入、关键字段变更审批、冻结/解冻/淘汰的W7–9首版见 ../lifecycle/README.md。绩效自动等级和后续RFQ等门户菜单未交付，对应编号保持PARTIAL。
