# SRM PRD 全模块差距复核

复核日期：2026-11-04
复核依据：docs/requirements/SRM需求规格说明书(PRD定稿).md、docs/requirements/SRM功能需求拆分.md、docs/requirements/SRM基于Snowy重建设计方案.md、docs/backlog.csv、docs/pilot/P8-114-acceptance-matrix.csv 及各模块实现/回归说明。

## 结论

此前的《SRM-全模块业务流手工验收用例》把 114 个 L3 需求压成了 24 条概览流程；用例没有关联具体 FR 编号，也没有逐条覆盖 PRD 的特异验收条件和通用 G1–G6。因此它不能作为“全模块逐项验收用例”。我之前把它称为全模块用例不准确。

按 backlog.csv，114 条需求中 86 条标记为“已实现”、28 条标记为“部分实现”；P8 矩阵仍将 114 条全部标记为待业务逐项验收。实现状态不表示 PRD 验收通过。

当前也没有一份按每条 FR 编号列出“已实现行为、缺失行为、证据、实操步骤、结果”的完整差距表。28 条 PARTIAL 的 P8“下一步”大多仍是通用文字“补齐该编号PARTIAL内容；验证PRD全部特异AC及G1–G6”，不足以指出具体剩余功能。因此下表把“实现未完成”与“24条用例没有覆盖/证据不足”分开；未有逐项代码或UI证据的内容标为待核实，不直接臆断功能不存在。

## 按模块复核

### M1 供应商准入与生命周期（CORE）

状态：28 条中 5 条 PARTIAL。

- CORE-103：PRD要求档案详情包含档案、资质、联系人、绩效、风险、订单等关联信息；当前证据需要逐个核对完整 Tab、数据范围、空态和数据新鲜度。
- CORE-104、CORE-501：W38已统一关键字段变更路径：所有可编辑业务状态的名称、品类、信用代码、银行账号及开户行不能通过档案直改接口保存，只能提交 CHANGE；POTENTIAL/CORRECTION/QUALIFIED/FROZEN 均提供申请入口。地址继续直改并写签名审计和前后版本；批准后才回写关键字段，拒绝保留原值。Maven目标测试和前端构建通过；W38浏览器业务验收及批准/驳回端到端流程尚待签收。
- CORE-303：联系人多角色、枚举校验和至少保留一个 ADMIN 的服务端约束；前端角色矩阵不等于所有联系人角色和服务端写权限均完成业务验证。
- CORE-403：两级准入节点已有流程；PRD还要求采购经理结合品类必要性、绩效决策并留意见。现有四账号由 admin 先后承担 SQE 与经理节点，能验证两个节点，不能验证两名独立审批人的职责分离。
- CORE-601：风险高等级触发原冻结审批已实现并有 W30 证据；手动冻结入口、冻结后对 RFQ/PO/竞价的全链路阻断、边界权限及错误恢复仍须按 PRD 单独验收。
- CORE-603：淘汰流程存在，但需逐项验收终态归档、历史可读、不可恢复，以及所有新 RFQ/PO/竞价入口均被阻断。

24条概览用例漏项：完整详情关联信息、资质分类/过期状态和提醒收件人、联系人逐角色启停和最后管理员保护、变更前后版本与冲突、冻结/淘汰后各业务入口阻断、准入拒绝/补正次数上限、列表组合筛选和脱敏 Excel 导出。

### M2 寻源（SRC）

状态：19 条中 1 条 PARTIAL（SRC-402）。W12–15 既有用例已覆盖报价、竞价主线的一部分；不能据此认为 PRD 所有 SRC AC 均覆盖。

- SRC-402 的主要缺口是定点申请中的绩效与风险证据、风险例外确认，以及审批的驳回、转办/改派和留痕是否完整形成一条可由现有账号执行的流程。已存在自动化证据，但本轮 24 条概览没有记录这些分支。
- 需补的逐项验收包括：RFQ 草稿保密、合格供方/品类候选过滤、发布后字段锁定、无报价撤回、延期通知、公开问答/私聊问答、报价金额计算与多轮历史、基准价盲化、到厂价归一化和固定权重、导出。
- 反向竞价需单列合法/非法降幅、匿名价与个人报价隔离、并发版本冲突、防狙击连续延时、无人报价流标、断线重连/轮询降级、Redis故障暂停和恢复、出价审计。24条概览未覆盖这些状态分支。

### M3 采购协同（COL）

状态：18 条中 2 条 PARTIAL。当前本地沙箱已覆盖订单、供方确认、ASN、收货、对账、发票及回执演示；它不是实际系统联调。

- COL-101：真实 ERP 主数据/PO/价格同步、主键幂等、失败重试和补偿仍未完成。
- COL-503：真实财务共享发票推送及正式回执仍未完成。用户已要求外部接口先不做，故应登记为“外部联调待后续”，不能混写为内部流程缺失，也不能用本机模拟回执宣称已完成。
- 内部业务还应逐项覆盖：PO 版本变化后的重新确认、ASN分批/超量、迟交提醒、部分收货与最终收货、容差配置版本、差异/争议升级、账单快照不可变、双方确认、人工收货冲销、发票金额校验及财务沙箱状态边界。

### M4 绩效与风险（PER）

状态：20 条中 5 条 PARTIAL。

- PER-102：月度评分依赖正式数据源/定时任务。测试导入或本地沙箱能验证算法，不代表 ERP/MES/QMS 月度数据汇入和生产调度完成。
- PER-104：评分明细需追到原始来源和单项指标；应核验详情不是只有总分、来源标识或聚合结果。
- PER-303、PER-304：QMS 来料结果正式回写及不合格自动扣分的真实来源、规则版本、重复/更正回执处理仍须确认；本地签名沙箱只证明本地协议路径。
- PER-504：内部风险分级、高风险自动建冻结待办已有局部验证；风险处置闭环、来源证据、预警对象、归档和解除/不解除冻结规则需独立验收。
- 24条概览未细分：指标/权重配置校验（30/35/20/15且合计100）、评分重算幂等、月度趋势/等级阈值、分项来源、门户申诉—SQE复核—重算、质量扣分规则与重复缺陷升级。

### M5 供应商门户（POR）

状态：14 条中 4 条 PARTIAL；W26与W33有阶段性交付，但不是全套门户 AC 的签收。

- POR-101：外部注册、一次性邀请、服务器绑定组织、生成潜在档案、审核前阻止业务的完整自助链路需要按 PRD 逐步验证。
- POR-103：W26 工作台已增加汇总卡片；需核验是否完整聚合待办、预警和绩效概览，是否与业务列表数量一致，失败区块/空状态和各联系人可见数据是否符合 PRD。
- POR-401：两个现有门户账号绑定同一供方，无法在主实例做“供应商 A 无法读取供应商 B”的浏览器验收。隔离副本的 API 测试不能替代主实例的多供应商UI验收。
- POR-402：PRD列出 ADMIN/QUOTE/SHIP/QUALITY/FINANCE 五类角色；当前仅有两个门户账号且都属于同一企业，无法用现有登录账号逐角色走完全部页面及写操作。不要为了测试擅自增加主实例账号；需在隔离副本建角色矩阵测试数据。
- 24条概览没有列出注册的邀请码/失效、五角色菜单与写权限、浏览器无越权请求、附件权限、账号停用后会话撤销等独立用例。

### M6 工作流（FLOW）

状态：9 条中 2 条 PARTIAL；FLOW-103 的代码实现已完成，P8 浏览器业务验收仍待签收。

- FLOW-101：W34 图形工具仅能对受控模板调整布局/节点显示名称；不支持设计新的审批拓扑、改变业务顺序/角色。若按 PRD“上传或在线设计”理解为完整在线设计器，该编号仍未完成；若只要求受控流程模板管理，需要业务方明确验收口径。
- FLOW-103：W37已补 8 类工作流分类映射的管理员维护页、V10 加法迁移、唯一约束/行版本及角色校验；Maven core/flow 测试和前端生产构建通过，流程键不变。自动实现状态已记为 IMPLEMENTED；浏览器业务验收及迁移升级实操尚未签收，不能据此关闭 P8 业务验收矩阵。
- FLOW-203：W27新增已办/审批历史页面，但 P8仍标 PARTIAL；需要验证所有流程类型的全链路历史、范围过滤、节点意见/时间和长期审计证据，不应只按“历史列表打开成功”关闭。
- 概览用例没完整覆盖发布新版本、挂起阻止新申请、旧实例绑定旧版本、审批转办/加签权限、超时催办幂等、TaskListener失败补偿和跨插件流程变量。

### M7 集成（INT）

状态：6 条全部 PARTIAL。依照用户指示，ERP、MES、QMS、财务共享、企微/钉钉等真实外部联调暂不安排。当前本机签名回调与故障注入属于本地模拟，不能改变此状态。

- INT-101–104：正式系统适配、凭证/密钥配置、字段映射、生产回执、失败重试与补偿待外部资料和联调环境。
- INT-105：真实消息 Webhook 未配置；本地站内消息不等于企微/钉钉送达。
- INT-106：监控记录可以本地演示；SLA 99.5%、持续监控、告警和自动补偿没有生产运行证据。

## 所有模块共同漏掉的 PRD 验收条件

24条概览没有为每个列表/写操作重复检查以下通用 AC，因此不能据此关闭任何 L3：

- G1：每个主列表的分页、主要筛选/排序和脱敏 Excel 导出。
- G2：必填/格式/唯一性错误文案；签名审计记录完整且敏感内容不泄漏。
- G3：内部 org 与本人/组织/全量数据范围；门户 trusted supplier_id，跨供方拒绝。
- G4：信用代码、银行账号、手机号、报价的 SM4 落库和角色级脱敏。
- G5：标注流程的状态只能经 Flowable/TaskListener 更新；异常回写的补偿或告警。
- G6：同步幂等、重试、重复请求、并发更新/竞价时的单一结果。
- 非功能：万级数据列表 P95<1s、最多50受邀方竞价广播<500ms、月度评分全量≤2小时、签名日志≥5年、Chrome/Edge版本验证、PostgreSQL/MySQL兼容矩阵和等保/信创验收证据。

## 账号、环境和验收限制

- 两个门户账号均绑定同一供方，主实例不能直接验证跨供方页面隔离，也无法产生真实多供方报价排名；相关场景要在隔离副本验证。
- 仅有 lijunhua 和 admin 两个内部账号，admin 同时承担SQE和经理节点。流程的两个审批节点可运行，但不能据此证明独立人员的职责分离策略。
- 这次模拟只对部分 API 做了回归；没有在 Windows 浏览器逐页验证，也没有执行这份 MD 的 114 项逐条验收。因此上一份模拟报告只能作为选择性 API 证据。
- 外部联调按用户决定排除。其依赖模块需要使用明确标注的本地沙箱测试，报告中标成“本地演示通过/真实接口待联调”。

## 后续验收资料应怎样重做

1. 先将 PRD §12 统计修正为 114 条，并以 backlog.csv 的 114 个编号作为唯一L3基线。
2. 将当前 24 条概览降为跨模块主线导航；另建逐项验收表，每个 FR 编号至少有：PRD AC原文/拆分检查点、前置数据、具体账号、页面路径和步骤、预期状态/字段、通过/失败/阻塞、不足说明、证据链接。
3. 将 G1–G6 作为每个适用 L3 的强制检查列；把列表、权限、敏感字段、审批、幂等和并发结果写成可观察预期，而不是只写“符合PRD”。
4. 对28个 PARTIAL逐条补充剩余 AC 与代码证据；对 INT-101–106及COL-101/COL-503等真实外部依赖标成延期项，不混入本机功能“已完成”。
5. 以隔离副本覆盖多供应商、多联系人角色、独立审批人等当前主实例账号无法安全覆盖的用例；用户主实例仅跑新建验收记录和只读场景。
